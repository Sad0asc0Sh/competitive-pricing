# موتور تطابق محصول v2 (نسخهٔ ۴.۲.۰)

> هدف این سند: توضیح اینکه چرا «کارت اشتباه ترب» دیگر خودکار قیمت‌گذاری نمی‌شود، قواعد دقیقاً چیست، چقدر اندازه‌گیری شده، و **کجا هنوز ناقص است**.
> کد: `src/lib/pricing/matcher.ts` و `src/lib/pricing/match/{parse,compare,lexicon,text}.ts` — آزمون‌ها: `tests/matcher-v2.test.cjs`.

---

## ۱. مسئله: چرا v1 قیمت اشتباه تولید می‌کرد؟

قیمت‌گذاری رقابتی فقط وقتی درست است که «کارت ترب» **همان کالای ما** باشد. در v1 امتیاز تطابق عمدتاً جمع شباهت واژه‌ها بود؛ نتیجه (اندازه‌گیری روی پیکرهٔ مصنوعی ۱۰۶۸ کیس، پیش از هر تنظیمی):

- مدل‌های هم‌خانواده (`DS-2CD1023G0E-I` در برابر `…-IF`) و پسوندهای متفاوت **بالای ۸۰٪ و خودکار** تایید می‌شدند؛
- کالای بدون کد مدل فقط با واژه‌های عمومی («دوربین مداربسته دام …») تایید می‌شد؛
- لوازم جانبی (براکت، کاور، لنز، آداپتور)، پک چندتایی، کالای استوک و کپی با کارت کالای اصلی اشتباه گرفته می‌شد؛
- از ۱۰۶۸ کیس، در ≈۲۷٪ کیس‌ها یک کارت **اشتباه** خودکار تایید شد.

هر تایید اشتباه، یک قیمت نهایی اشتباه است که مستقیم به فروشگاه ارسال می‌شود (هرچند موتور بعدش کف سود را رعایت می‌کند، «کف سود» ما را از **فروش با قیمتِ کالای دیگر** نجات نمی‌دهد).

## ۲. اصول طراحی

1. **تایید خودکار فقط با «شناسایی مثبت».** یعنی کد مدل یکسان یا هم‌ارز، یا (برای کالای بی‌کد) مشخصات کامل و راستی‌آزمایی‌شده. شباهت متنِ زیاد، به‌تنهایی کافی نیست.
2. **وتو (Veto):** نشانهٔ قطعیِ «کالای دیگر» (لوازم جانبی، پک، استوک، کپی، رده/برند/کد/مشخصات متضاد) امتیاز را به ناحیهٔ **رد** می‌برد.
3. **قفل (Blocker):** ابهام (کد ناقص، پسوند متفاوت، برند نامعلوم، مشخصهٔ راستی‌آزمایی‌نشده) تایید خودکار را قفل می‌کند و به **بازبینی انسانی** می‌فرستد (سقف امتیاز = `max(رد+۵, تایید−۶)` = ۷۴ با آستانه‌های پیش‌فرض ۴۵/۸۰).
4. **امتیاز = احتمال هم‌هویتی:** لجستیک روی شواهد (`sigmoid(logit)`) و سپس محدودشده با وتو/قفل. شفاف: هر امتیاز فهرست دلیل (`notes`) و علت قفل (`blockers`) دارد که در صف بازبینی نشان داده می‌شود.
5. **تصمیم‌ناپذیری = بازبینی، نه حدس.** هزینهٔ بازبینی کم، هزینهٔ تایید اشتباه زیاد است.

## ۳. گام‌های مقایسه (`compareParsed`)

هر عنوان (فروشگاه/ترب) ابتدا به ساختار تبدیل می‌شود (`parseTitle`): برندها، کدهای مدل (کانونیک‌شده: حروف بزرگ، بدون خط‌تیره/فاصله، با بخش‌های سگمنت)، رده/نوع کالا (head noun)، ویژگی‌های فرعی (بولت/دام، IP/آنالوگ…)، مشخصات تایپ‌شده (مگاپیکسل، کانال، ظرفیت، پورت، ولتاژ، آمپر، طول، Cat، …)، نشانگرهای ریسک (پک، استوک، کپی، معیوب) و واژه‌های توصیفی. شناسه‌های داخلی (`ObjectId` مونگو، `KY-1234`، SKU عددی صرف) **هرگز کد مدل حساب نمی‌شوند** (`isInternalOrDatabaseId`).

سپس به ترتیب:

| گام | بررسی | اثر |
| :-- | :-- | :-- |
| ۱ | نشانگرهای ریسک (کپی، معیوب، استوک، پک/باندل، مجموعهٔ ترکیبی) | وتو با سقف ۴ تا ۱۰ (سایت ← ترب نامتقارن؛ «سایت استوک ولی ترب نو» فقط قفل) |
| ۲ | رده/نوع کالا + ویژگی‌های فرعی (فرم، فناوری، نوع هارد/ضبط) | رده متضاد ⇒ وتو (۸)؛ ترب «لوازم جانبی» ولی سایت «کالای اصلی» ⇒ وتو (۵)؛ تضاد فرعی با کد یکسان ⇒ قفل |
| ۳ | برند (با «برند مادر» و زیربرند؛ مثلاً HiLook⟵Hikvision، Imou⟵Dahua، Tapo⟵TP-Link) | برند متضاد ⇒ وتو (۲۲)؛ با کد یکسان فقط قفل |
| ۴ | رابطهٔ کد مدل (جدول بخش ۴) | ستون فقرات هویت |
| ۵ | قفل‌های وابسته به برند برای کدهای کوتاه/هم‌ارز | کد ≤ ۶ نویسه بدون برند مشترک ⇒ قفل |
| ۶ | مشخصات تایپ‌شده (اصلی در برابر فرعی) | تضاد اصلی ⇒ وتو (۱۸) (یا قفل اگر کد یکسان)؛ تضاد فرعی (لنز/Wi-Fi/IP-rating) با کد یکسان فقط یادداشت |
| ۷ | واژه‌های توصیفی (پوشش) | مهم‌تر برای کالای بی‌کد؛ نام سری لاتین یا واژهٔ نوع‌ساز فقط-در-ترب ⇒ قفل |
| ۸ | نسبت قیمت کارت ترب به لنگر محصول | بخش ۶ |
| ۹ | معیار تایید برای کالای بی‌کد | بخش ۷ |

## ۴. رابطهٔ کدهای مدل (`relateCodes`)

| رابطه | معنا (مثال) | رفتار |
| :-- | :-- | :-- |
| `equal` | کانونیک یکسان | شناسایی مثبت (بالاترین وزن) |
| `alias` | یکی فقط پیشوند برند دارد (`DS-2CE76D0T-ITPFS` ⟷ `2CE76D0T-ITPFS`) | شناسایی مثبت؛ کد کوتاه یا بدون برند مشترک ⇒ قفل |
| `tail` | کد سایت بخشِ انتهایی کد ترب است | شاهد ضعیف ⇒ همیشه قفل (بازبینی) |
| `ext_seg` | یک سگمنت اضافه/کم (`…1431S` ⟷ `…1431S-S4`) | احتمالاً نسخهٔ دیگر ⇒ قفل |
| `stem` | یک طرف فقط «ریشهٔ مدل» است (طول < ۸۰٪) | ابهام ⇒ قفل |
| `ext_chars` | حرف/رقم اضافه روی کد کامل (`…-I` ⟷ `…-IF`) | **مدل هم‌خانوادهٔ متفاوت ⇒ وتو (۲۰)** |
| `sibling` | فاصلهٔ ویرایشی کم (مدل مجاور) | **وتو (۲۰)** |
| `unrelated` | بی‌ربط | **وتو (۲۰)** |

قاعدهٔ «چند کد»: اگر محصول سایت چند کد دارد، همهٔ آن‌ها باید در کارت ترب پوشش داده شوند. اگر کارت ترب چند مدلِ هم‌خانواده را با هم ذکر کند ⇒ قفل.

## ۵. وتو در برابر قفل (چرا این تمایز مهم است؟)

- **وتو** = «شواهد می‌گویند کالا فرق دارد» ⇒ رد (`reject`)، کارت اصلاً در انتخاب نمی‌آید.
- **قفل** = «نمی‌توانم ثابت کنم یکی است» ⇒ بازبینی (`review`)؛ با تأیید انسان قابل‌قبول است.

یک استثنای هدفمند: وقتی **کد دقیقاً یکسان** است، تضادهای فرعی (لنز، Wi-Fi، IP-rating) فقط «یادداشت» می‌شوند و تضادهای اصلی/ساختاری «قفل»، نه وتو. دلیل: عنوان‌های ترب ناقص و پرغلط‌اند و کد یکسان قوی‌ترین شاهد است. (هزینهٔ این انتخاب در بخش ۱۰ آمده: H02.)

## ۶. قاعدهٔ نسبت قیمت

با `r = قیمت کارت ترب ÷ لنگر محصول` (لنگر = قیمت خرید مؤثر اگر موجود باشد، وگرنه قیمت نهایی فعلی):

| r | اثر |
| :-- | :-- |
| `< ۰٫۴۲` | وتو (سقف ۱۲) — احتمالاً قطعهٔ جانبی/کالای اشتباه |
| `> ۲٫۳` | وتو (سقف ۱۵) — احتمالاً پک چندتایی/مدل بالاتر |
| `< ۰٫۵۵` یا `> ۱٫۹` | قفل + کاهش امتیاز |
| `۰٫۸۵ … ۱٫۳` | تشویق نرم (+۰٫۵ لوجیت) |
| کالای بی‌کد | برای تایید خودکار باید `۰٫۶ ≤ r ≤ ۱٫۷` باشد |

در موتور، قیمتِ نمایندهٔ کارت = **میانهٔ قیمت‌های مثبت پیشنهادها** و تعداد فروشنده = `totalSellerCount`.

## ۶-ب. «قاعدهٔ ابهام بین‌کارتی» (انتخاب کارت از نتایج جستجو)

اگر در نتایج جستجو **دو کارت با هویت متفاوت** هر دو به حد «تایید خودکار» برسند، هیچ‌کدام خودکار نیست (هر دو به سقف بازبینی می‌روند و در یادداشت می‌آید «انتخاب با بازبین»). کارت‌های هم‌هویت (تکرار لیستینگ) فقط با ترتیب «موجود، سپس بیشترین فروشنده» مرتب می‌شوند.

## ۷. کالای بدون کد مدل (سیاست عمومی/Generic)

کالاهایی مثل «آداپتور ۱۲ ولت ۵ آمپر» یا «کابل HDMI ۵ متر» کد مدل ندارند. سیاست v2: خودکار فقط اگر **همهٔ** این‌ها برقرار باشد: رده یکسان، برند مشترک (یا هر دو بدون برند)، دست‌کم یک مشخصهٔ تایپ‌شدهٔ راستی‌آزمایی‌شده (یا پوشش کامل واژه‌های اختصاصی)، پوشش واژه‌های اختصاصی ≥ ۹۹٪ (یا ≥ ۷۵٪ برای عنوان‌های ≥ ۴ واژه‌ای)، نسبت قیمت ۰٫۶–۱٫۷، هیچ مشخصهٔ اصلیِ ذکرنشده در یکی از دو طرف، و نبودنِ نام سری/نسخهٔ لاتین یا واژهٔ نوع‌ساز فقط-در-ترب.

**این یک تصمیم سیاستی است، نه مطلقاً بی‌خطا:** برای کالای کاملاً عمومی، «همان مشخصات» در عمل «کالای قابل‌تعویض» است و ترب هم همین‌طور آن‌ها را ادغام می‌کند. اگر نمی‌خواهید این گروه هرگز خودکار شود، در `compare.ts` شرط `positiveId` گام ۹ را ببندید (یا لیست رده‌های مجاز را کوتاه کنید) — هزینه: بازبینی بیشتر.

## ۸. پیوند با موتور قیمت‌گذاری (گیت هویت)

`engine.ts` برای کارتی که **انتخاب شده یا از قبل ذخیره شده (prk)** هم گیت هویت را اجرا می‌کند (نمی‌توان به «پیش‌تر درست انتخاب شده» اعتماد کرد):

- امتیاز < خط رد (۴۵) ⇒ رد (علت در `reviewReasons` و گیت هویتِ ناظر SystemOne با `strictGateVeto` وتو می‌کند)؛ هیچ قیمتی خودکار اعمال نمی‌شود.
- امتیاز در ناحیهٔ بازبینی ⇒ فقط بازبینی.
- **حضور فروشگاه خودمان در لیستینگ ادغام‌شدهٔ ترب** «ابهام» را برطرف می‌کند (بازبینی ← تایید) ولی **هرگز** رد قطعی (کد متفاوت، لوازم جانبی، پک، استوک، تضاد مشخصات) یا رابطهٔ «نسخهٔ متفاوت» (`ext_seg`/`ext_chars`/`sibling`) را نمی‌پوشاند — چون در آن حالت یا ترب کارت را اشتباه ادغام کرده یا عنوان محصول ما غلط است. (سنجیده‌شده: سناریوی `wrongself` در بخش ۹.)
- عنوان کارت غایب ⇒ fail-closed: امتیاز هویت سقف ۷۰٪.

### ۹-پ) سرتاسر (موتور کامل روی شبیه‌ساز بازار)

دنیاهایی که در آن ترب کارتِ **محصول دیگری از همان خانواده (مدل خواهر)** را برای کالای ما برمی‌گرداند؛ پس «هر اعمال خودکار = یک خطای واقعی» است (۳ seed کنارگذاشته × ۳۰۰ = ۹۰۰ سناریو):

| حالت | v1: درصد اعمال خودکار (CI ۹۵٪) | v2 |
| :-- | :-- | :-- |

| `wrongself` — ترب فروشگاه ما را هم در همان لیستینگ ادغام کرده (سخت‌ترین حالت) | ۴۰٫۹٪ (۳۷٫۷–۴۴٫۱٪) | ۰ از ۹۰۰ (کران بالای CI = ۰٫۴۳٪) |

(`eval/results/wrong_listing_heldout.json`، `node eval/market/wrong.cjs`.) توجه: صفر مشاهده‌شده به‌معنای «احتمال صفر» نیست؛ کران بالای ۹۵٪ حدود ۰٫۴٪ است — و این فقط برای نوع خطای شبیه‌سازی‌شده (مدل خواهر) صادق است.

| **H16** کد با فاصله/خط‌تیرهٔ متفاوت (`DS 2CE16H0T ITPF`) | بازبینی | قالب‌های جداشده با فاصله کامل پارس نمی‌شوند | بهبود `parse.ts` |
| **H15** عنوان ترب بدون کد مدل | بازبینی | هویت فقط با مشخصات احراز نمی‌شود | درست است که بازبینی شود |
| **H20** گوشی با «رم ۶ گیگ» و «حافظهٔ ۱۲۸ گیگ» | بازبینی | رم و حافظهٔ داخلی هر دو «ظرفیت» پارس می‌شوند (`cap:[128,6]`) ⇒ عنوان «چندمقداره» حساب می‌شود | ایمن ولی پرهزینه؛ جداکردن رم از ظرفیت در `parse.ts` |
| SKU فروشگاه | اگر فقط SKU داخلی (مثل `KY-123`) باشد کد حساب نمی‌شود | کالا «بی‌کد» رفتار می‌کند | افزودن فیلد `mpn/model` به ایمپورتر (پیشنهاد، پیاده‌نشده) |

همچنین: واژگان ۵۰ برند (دوربین مداربسته/شبکه/ذخیره‌سازی/کامپیوتر) و ۳۴ رده (۱۶ کالای اصلی + ۱۸ لوازم جانبی/قطعه) دارد؛ برای دستهٔ دیگر (مثلاً لوازم خانگی) باید گسترش یابد وگرنه کدهای کوتاه بدون برند به بازبینی می‌روند (ایمن ولی پرهزینه).

## ۱۱. چگونه واژگان را گسترش دهیم؟

فقط `src/lib/pricing/match/lexicon.ts`:

```ts
// برند جدید
logitech: { aliases: ["لاجیتک", "لوجیتک", "logitech"] },
// زیربرند (تضاد برند با برند مادر را نرم می‌کند)
// tapo: { aliases: ["تاپو","tapo"], parent: "tplink" },
// پیشوند کد که فروشندگان حذف می‌کنند: codePrefixes: ["ds","ids"]
```

سپس:

```bash
npm test                                 # آزمون‌ها (matcher-v2 شامل موارد حداقلی)
node eval/matching/run.cjs --split all   # پیکرهٔ مصنوعی
node eval/matching/realistic.cjs         # مجموعهٔ توسعه
```

**قاعدهٔ صداقت:** مجموعهٔ `realistic2.cjs` پس از اولین اجرا و استخراج ایراد دیگر «کنارگذاشته» نیست. پس از هر اصلاح بر پایهٔ آن، مجموعهٔ تازه‌ای (مثلاً `realistic3.cjs`) بنویسید.

## ۱۲. پرچم‌ها و بازگشت امن

- `MATCHER_FLAGS` (در `matcher.ts`): `aliasCodes, tailCodes, headClass, riskMarkers, attrConflicts, brandConflicts, approveNeedsId, softPrice` — برای ablation و خاموش‌کردن اضطراریِ یک قاعده. **فقط سطح ماژول‌اند و در پروفایل/دیتابیس نیستند.**
- `estimator.mode = "legacy"` رفتار **قیمت‌گذاریِ** ۴.۱.۲ را بیت‌به‌بیت برمی‌گرداند (آزمون E1) ولی **تطبیق‌دهنده را برنمی‌گرداند**: امتیاز هویت و ناظر همچنان از matcher v2 می‌آید (عمداً سخت‌گیرتر؛ در ۳۰۰ سناریو ≈۲٪ تفاوت در صف بازبینی و صفر تفاوت قیمت). یعنی rollback یعنی «برگرداندن تخمین‌گر»، نه «برگرداندن ایمنی هویت».
